# КосмоХакатон 2026 — «Проектирование устойчивой спутниковой группировки»

Репозиторий: github.com/RAR939/Sat_control
Дедлайн: сжатые сроки (изначально 1,5 суток от 11 сентября 2026) — приоритизируй
рабочий минимальный путь над полнотой функционала.

## Что это за проект

Веб-сервис проектирования и анализа спутниковой группировки связи: 48
спутников на орбите 550 км, 3 орбитальные плоскости по 16 аппаратов, запуск в
3 очереди (launch_stage). Сервис должен считать покрытие северных наземных
точек-клиентов, строить маршрут связи через сеть спутников до наземного
шлюза, обрабатывать отказы спутников/шлюза, сравнивать конфигурации между
собой. Целевая доступность (`target_availability`) — 90% времени на клиента.

Стек: Python (FastAPI) backend + React frontend. Backend переиспользует уже
готовый `geometry.py` (см. ниже) как нижний расчётный слой — не переписывать
его без необходимости.

**Критично для защиты:** жюри само загрузит другой сценарий того же формата
и покрутит параметры через интерфейс. Сервис не должен быть захардкожен под
4 демонстрационных JSON-файла — он обязан работать с произвольным валидным
сценарием этой схемы.

## Формат входных данных (schema `cosmo-A-1.0`)

```
environment: altitude_km, inclination_deg, earth_angle0_deg, horizon_s,
             step_s, min_elevation_deg, isl_range_km, target_availability
design.planes: [{id, raan_deg, phase_deg}, ...]
design.satellites: [{id, plane_id, slot_deg, launch_batch}, ...]
design.launch_stage: 1 | 2 | 3
ground_sites: [{id, role: "client"|"gateway", lat_deg, lon_deg}, ...]
failures: [{satellite_id, start_s, end_s}, ...]
gateway_outages: [{gateway_id, start_s, end_s}, ...]
```

`geometry.py` (уже есть в проекте) предоставляет: `load`, `validate`,
`positions`, `snapshot(scenario, t_s)` — возвращает позиции спутников,
активность, ISL-рёбра, elevation к наземным точкам. Там же есть функция
`sunlight` — она НЕ используется в этой задаче (это про затенение Землёй для
энергетики, к связи отношения не имеет), можно игнорировать полностью.

## Принятые архитектурные решения (не пересматривать без причины)

- **Маршрутизация — BFS**, не DFS. Multi-source: от множества спутников,
  видимых клиенту, к множеству спутников, видимых шлюзом. BFS даёт кратчайший
  по числу хопов маршрут бесплатно (та же асимптотика, что и DFS), что важно
  и для визуализации на карте, и как честная метрика в отчёте.
- **Проверка валидности маршрута перед пересчётом**: если маршрут остался с
  прошлого шага, сначала проверяем, что все его рёбра ещё существуют в
  текущем графе (дёшево — просто пробег по паре десятков узлов), и только
  если невалиден — пересчитываем BFS и фиксируем факт перестроения маршрута.
- **Хранить полные снэпшоты состояния на каждом шаге времени**, не diff'ы —
  при 720 шагах и 48 спутниках это не тяжело по памяти, а код и отладка
  сильно проще, чем при инкрементальном хранении.
- **4 причины отсутствия маршрута**, проверять строго в этом порядке:
  1. `NO_VISIBLE_SATELLITE` — у клиента нет ни одного видимого спутника
  2. `GATEWAY_UNAVAILABLE` — шлюз в состоянии outage в этот момент времени
  3. `NO_GATEWAY_CONNECTION` — ни один спутник геометрически не видит шлюз
     (даже без учёта outage)
  4. `BROKEN_ISL_NETWORK` — компонента связности от клиента не достигает ни
     одного спутника, видимого шлюзом (разрыв межспутниковой сети)
- **3D-визуализация не в приоритете** — используем 2D-карту (equirectangular
  проекция: спутник из fixed XYZ переводится в lat/lon обратным пересчётом).
- **Весь код — с докстрингами и комментариями там, где логика неочевидна**
  (не комментировать тривиальные строки построчно — это трата времени).
  Требуется документация для сдачи проекта.

## Разделение работы

- Пункты 1-4 плана (граф на момент t → BFS-маршрутизация → проверка/
  перестроение маршрута → сохранение состояний по времени → доступность и
  причины outage) — делает другая часть команды, статус уточнить у них.
- Пункты 5 (анализ устойчивости) и 6 (автоподбор конфигурации) — уже
  написаны и протестированы, см. ниже.
- Автоматическая оптимизация стратегий маршрутизации и сравнение алгоритмов
  BFS vs альтернативы — сознательно вырезано из скоупа (баллов не даёт, время
  дороже выгоды). Не реализовывать, если явно не попросят вернуть.

## Что уже готово (перенести в репозиторий, если ещё не перенесено)

`resilience.py` + `test_resilience.py` — анализ устойчивости, три уровня:
- `analyze_resilience(scenario, simulate_fn, branch=1)` — отказ одного
  спутника за раз, рейтинг по падению МИНИМАЛЬНОЙ (не средней) доступности
  среди клиентов.
- `analyze_resilience_staged(...)` — top-K критичных из branch=1, затем
  перебор пар только среди них (дёшево, но принципиально не находит пары
  спутников, безобидные поодиночке — это задокументировано в докстринге).
- `analyze_group_resilience(...)` — отказ целой орбитальной плоскости или
  партии запуска целиком (дёшево: число прогонов = число групп, а не
  комбинаторика); закрывает слепую зону staged-метода для физически
  правдоподобных корреляций отказов.

`optimization.py` + `test_optimization.py` — автоподбор RAAN/phase:
`optimize_configuration(scenario, simulate_fn, ...)` — случайный поиск по
всему пространству параметров + локальное уточнение (coordinate
hill-climbing) вокруг лучших находок. Полный grid search по 6 непрерывным
параметрам (RAAN+phase на 3 плоскости) физически нереален; градиентные
методы (backprop) не применимы — расчёт видимости и BFS-маршрутизация
недифференцируемы по параметрам (пороговые функции, комбинаторная структура
графа).

**Оба модуля не содержат расчётной логики симуляции.** Они принимают
`simulate_fn: Callable[[dict], SimulationResult]` как параметр (dependency
injection) — где `SimulationResult.clients` это список
`ClientAvailability(client_id, availability, max_outage_s, total_outage_s)`.
Это осознанное решение: модули можно было писать и тестировать независимо от
готовности пунктов 1-4. Протестированы на моках, оба теста проходят.
